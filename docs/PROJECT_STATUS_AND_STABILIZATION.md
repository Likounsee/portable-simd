# Portable SIMD — project status and stabilization assessment

**Assessment date:** 2026-11-22  
**Repository:** [Likounsee/portable-simd](https://github.com/Likounsee/portable-simd)  
**Baseline:** first CI run, commit `664729f4ecc4cd6c9bfc4d966c2194004f1cf550`  
**Assessed code head:** `afc31bcbdd980454cf122d5c281e430e4552132c`

## Executive summary

This fork has moved from an initially failing validation setup to a substantially better-tested and more observable development branch. The most important progress is in regression coverage for masks, masked memory, gather/scatter, dynamic swizzling, integer edge cases, SIMD layout, and in making CI reproducible across a broad target matrix.

This is **not yet a stable-ready implementation**, and the work so far does not demonstrate that a previously exploitable memory-safety bug in the SIMD implementation has been fixed. Security-related progress includes stronger verification of bounds and disabled-lane behavior, explicit size/alignment tests, panic-safe test-helper cleanup, and lane-wise use of Rust's strict-provenance pointer APIs. Confirmed production changes also include bounded/full-width slice-memory fast paths and f16 support additions. These are focused changes, not a broad rewrite or a proof of soundness.

The fork's GitHub Issues feature is disabled and the fork has no issue tracker of its own. The upstream `rust-lang/portable-simd` repository reports 107 open issues at the time of this assessment. This document therefore classifies the 16 upstream issue numbers explicitly investigated in this fork's development log; it does **not** claim to have resolved or audited all 107 upstream open issues.

## 1. Baseline: the first CI run

The first recorded CI run was [run 43384863663](https://github.com/Likounsee/portable-simd/actions/runs/43384863663), run number 1, on commit `664729f`.

- 30 jobs were reported.
- 29 failed and 1 was cancelled.
- The failures were not 29 independent SIMD correctness defects.
- A major repeated compile failure was that helper items on the mask element trait had been made private even though sibling implementation modules still needed them. Miri and multiple architecture jobs consequently failed before running their tests.
- The formatting job also rejected the newly added masked-memory tests.
- The logs show compile-time visibility errors for `TRUE`, `FALSE`, and `max_unsigned`, plus rustfmt differences.

The visibility issue was corrected by keeping the implementation helper crate-visible while preventing downstream users from accessing it through the public trait surface. Compile-fail coverage was added for downstream access. The formatting failures were corrected separately.

This distinction matters: the first CI was primarily exposing integration/visibility and test-formatting problems, not proving that all the architecture backends or SIMD arithmetic were broken.

## 2. What has materially improved since baseline

The baseline commit and assessed head differ by 510 commits. The changes fall into these groups.

### A. Mask semantics and mask safety invariants

- Added exhaustive ordering coverage for 8-lane masks (all 65,536 pairs of patterns), plus wider/high-bit cases.
- Added bitmask conversion tests at lane-count boundaries, odd widths, and the 64-lane boundary. Expected values are computed independently rather than relying only on a round trip.
- Added first/last-set lane boundary tests over the lane widths generated by the test helpers.
- Kept the mask validity invariant in place; no safety assumption was removed to chase code generation.
- Restricted implementation-only mask helpers so downstream code cannot depend on them, while sibling crate modules can still use them.

**Impact:** substantially better confidence in lane ordering, bit ordering, conversion boundaries, and encapsulation. This is stronger regression protection, not proof that all mask code generation or representation issues are solved.

### B. Masked memory, gather and scatter

- Added scalar-oracle tests for masked contiguous load/store and gather/scatter.
- Covered empty and short slices, disabled lanes, invalid indices, `usize::MAX`, and fallback values.
- Added width coverage at representative sizes from 1 through 64, including non-power-of-two widths.
- Added slice-length sweeps, full-width and over-width cases, shifted element offsets, and destination-tail/canary checks.
- Exhaustively enumerated 625 four-lane scatter index tuples and all 16 masks.
- Tightened the duplicate-index scatter oracle to require the documented highest-enabled-lane winner.
- Added a further gather boundary sweep at every tested lane width, rotating valid indices, the slice-length boundary, vector-width boundary, and `usize::MAX`.

**Impact:** much stronger evidence that safe masked APIs respect bounds, fallback semantics, disabled lanes, and documented collision behavior. These tests do not replace Miri, sanitizer testing, or a proof/review of the unsafe implementation.

### C. Dynamic swizzle

- Added a scalar-oracle test that visits every possible `u8` index at representative widths around implementation boundaries.
- Added `swizzle_dyn_unchecked` with an explicit high-bit out-of-range contract and exhaustive high-bit regression tests.
- Added architecture-specific implementations for AArch64/ARMv7, WebAssembly SIMD128, x86 SSSE3/AVX2 and LoongArch LSX/LASX checked swizzles; unsupported cases retain the scalar or split-vector fallback.

**Impact:** both checked zeroing semantics and the constrained unchecked API now have regression coverage. Architecture-specific execution still depends on the CI target-feature matrix.

### D. Integer and floating-point edge cases

- Added signed division/remainder boundary tests, including signed minimum values and mixed lanes, and registered them across the lane-width test helper.
- Added halfway-value tests for floating-point rounding.
- Added f16 SIMD iterator sum/product support and bit-preserving native/big-endian/little-endian byte conversions with NaN-payload and signed-zero test patterns.
- Kept approximate ULP comparisons for transcendental functions where platform libm results are not bit-identical.

**Impact:** better regression protection around known edge cases and cross-platform numerical variability. The historical AArch64 LLVM ICE report still needs a minimal compiler-only reproducer before it can be declared fixed.

### E. Layout and pointer safety documentation

- Expanded SIMD layout regression coverage, including `f16`.
- Corrected the earlier documentation about possible trailing padding after tests established equal size for supported SIMD and array types in the covered layout matrix.
- Clarified that equal size does not make references interchangeable and does not waive pointer validity, initialization, aliasing, or provenance requirements.
- Replaced pointer-vector/integer transmute-based address conversions with lane-wise calls to scalar strict-provenance APIs for `addr`, `without_provenance`, and `without_provenance_mut`; `with_addr` also uses the scalar strict-provenance API lane by lane, avoiding integer-difference emulation.
- Clarified that unaligned reads/writes still access the full SIMD object size.

**Impact:** clearer unsafe contracts and broader layout assertions. This is not a substitute for a compiler guarantee about every target ABI/layout or every future element type.

### F. Confirmed implementation and code-generation work

- Added a fork-linked diagnostic benchmark and CI artifact generation for optimized SSE2 assembly and LLVM IR.
- Corrected the benchmark so it links the fork's `core_simd` crate rather than accidentally measuring the toolchain's `std::simd`.
- Added a full-width all-enabled path for `load_or` and `store_select`: complete vectors use the existing SIMD load/store helpers; short slices retain bounded prefix handling and fallback behavior.
- The inspected fork-linked SSE2 artifact showed vector loads/stores (`movups`) for full-width all-enabled operations. Short-prefix paths retain bounded `memcpy` handling. Sparse masked stores still lower to per-lane conditional scalar stores on SSE2, which has no general masked-store instruction; this remains a target/codegen optimization opportunity, not a correctness failure.
- Added regression tests for the fast path, short slices, offsets, and tail preservation.

**Impact:** this is a real production-code optimization supported by generated-code inspection. It is not yet a measured speedup claim: controlled timing comparisons across targets are still missing. Sparse-mask paths have not been comprehensively reworked.

### G. CI reliability and breadth

- Fixed the first-run mask-helper visibility failures and formatting failures.
- Fixed native CPU cache reuse across runners after an AVX-512-capable build artifact caused SIGILL on a runner without AVX-512.
- Fixed Cross installation/cache setup failures and prepared Cross once before the emulated target fan-out.
- Consolidated workflow jobs without removing the existing x86 target/feature, debug/release, Clippy, WASM, macOS, Cross, or Miri test categories.
- Added reproducible codegen diagnostics as a separate quality check.
- Added a compile-only x86 AVX-512 swizzle check that enables the exact target features required by the byte-minimum and byte-permute intrinsics without executing those instructions.

The historical fully green run recorded earlier is [run 43734489259](https://github.com/Likounsee/portable-simd/actions/runs/43734489259), on commit a15f086: 30/30 jobs succeeded. The most recent run inspected during the 2026-11-22 follow-up was [run 45066299426](https://github.com/Likounsee/portable-simd/actions/runs/45066299426), on commit `ad51b01a4a219a529a471bc812e6af547fbbc7ad`. It completed 19 jobs successfully with no recorded failures; the remaining 11 jobs were cancelled after later pushes. This is not a completed green matrix. The current main head at the time of this report update has no completed full CI run verified. No current-head green claim is made.

### H. Example correctness and documentation follow-up

- Fixed the SIMD dot-product example variants that previously ignored trailing elements when the input length was not divisible by four.
- Added coverage for all remainder lengths over input sizes 0 through 17, and made every dot-product variant enforce equal input lengths.
- Made the spectral-norm example reject a zero-sized matrix explicitly rather than return NaN from a zero-over-zero calculation.
- Corrected the examples guide so its command runs the dot-product regression tests and refers to the current `core_simd` crate name.

**Impact:** the examples now cover their documented input lengths and reject invalid shape combinations consistently. These are example/API-usage corrections, not changes to the SIMD compiler intrinsics.

### Additional codegen issue reviewed: upstream #321

[#321 — SIMD functions sometimes scalarize after inlining](https://github.com/rust-lang/portable-simd/issues/321) reports an AArch64 case where a 32-lane byte-vector predicate has good standalone assembly but scalarizes heavily when inlined into an iterator loop. The discussion identifies LLVM instruction selection / reduction lowering as the likely layer, not a demonstrated defect in the portable-simd Rust implementation. A later report (2025-01-30) says a then-current nightly generated much better assembly, though possibly not optimal.

Disposition for this fork: **investigated, not claimed fixed**. This is a useful regression target for future AArch64 codegen artifacts, especially around mask reductions and inlining. It should be tested against the current compiler before any library workaround is considered. The existing SSE2 masked-memory artifact does not cover this scenario.

### Additional API/codegen issue reconnaissance: upstream #475, #479 and #240

- [#475 — `Simd::gather_unchecked()`](https://github.com/rust-lang/portable-simd/issues/475) is implemented in `crates/core_simd/src/vector.rs`. It documents the all-lanes-in-bounds precondition and delegates to the pointer-gather primitive with all lanes enabled. This closes the API-availability gap in the fork; the upstream codegen concern still needs target-specific measurement.
- [#479 — add `to_mask` to `Simd`](https://github.com/rust-lang/portable-simd/issues/479) is implemented in the fork through `SimdInt::to_mask`, `SimdUint::to_mask`, and `SimdFloat::to_mask`. The methods convert each lane by comparison with zero; floating-point NaN maps to true and both signed zeros map to false. The unsigned method uses the mask type supplied by `SimdPartialEq` rather than adding a new associated type. Compilation, API review, and full target validation remain required.
- [#240 — masked compress-store / expand-load](https://github.com/rust-lang/portable-simd/issues/240) remains open; its linked duplicate #241 was closed at filing time. The current `vector.rs` API contains no compress/expand operation. This is a potentially useful API gap for filtering/packing workloads, but the proposal depends on portable compiler intrinsic support and semantics for unused lanes. Track it as an upstream API/compiler dependency rather than implementing target-specific behavior in this fork.

These three supplementary investigations are not added to the 16-item implementation issue count above; they are separate API/codegen observations.

### Cross-cutting stabilization blocker: upstream #364

The upstream meta-issue [#364 — Critical issues before stabilization](https://github.com/rust-lang/portable-simd/issues/364) is still open (last updated 2026-08-04). It is separate from the 16 issue references inventoried in the development log and should be treated as a key API-readiness checklist, not as a single implementation bug.

Its unresolved design topics include:

- **Supported lane counts:** whether the current lane-count bounds remain part of the public generic API or can be replaced by compiler-enforced post-monomorphization constraints. This affects generic ergonomics and requires compiler/API agreement.
- **Mask element type and representation:** whether masks for different SIMD element types should retain the current associated-element relationship or move to a more explicit mask abstraction. This is a potentially breaking public type-design decision.
- **Swizzle API:** const/dynamic swizzle ergonomics remain constrained by language and LLVM capabilities. The current fork's exhaustive tests validate today's zeroing behavior; they do not settle the long-term API.
- **Trait/API organization and feature partitioning:** the upstream discussion also raises high-level documentation, trait structure, and splitting independently stabilizable API areas.

No local implementation change can responsibly settle these design choices without maintainer consensus. Before any stabilization proposal, this fork should map every public item to the upstream decision and record whether it is accepted, deferred, or blocked. The upstream discussion also records a separate need for reviewed intrinsic safety requirements and documentation (tracked there by #381).

## 4. Current readiness assessment

### What is in good shape

- The fork has a reproducible, broad CI matrix and a confirmed fully green run on `a15f086`.
- Miri is part of CI in four shards.
- Tests now cover several high-risk semantic boundaries for masks, gather/scatter, masked memory, dynamic swizzle, layout, and integer edge cases.
- The first known CI integration failures (especially mask helper visibility and formatting) were corrected.
- One targeted production memory-path optimization has codegen evidence.
- Unsafe pointer and layout documentation is clearer than at baseline.

### What is not yet established

- The current main head at the time of this report update still needs its own completed green CI run.
- No full unsafe-code audit has been completed across all modules and architecture backends. A first-pass inventory has begun for vector.rs, masks.rs, select.rs, pointer SIMD modules, and std_float; it is not yet a reviewed safety audit.
- Miri passing is valuable but does not prove absence of undefined behavior; target-specific hardware/emulator coverage also has limits.
- The #427 historical compiler ICE lacks a minimal compiler reproducer.
- #472, #495, and #539 depend substantially on compiler/backend or API-contract work.
- #341/#343/#494 need broader LLVM IR/assembly inspection and controlled benchmarks, not only an SSE2 example.
- No controlled performance suite currently demonstrates end-to-end gains or guards against regressions across x86, AArch64, WASM, and emulated targets.
- No independent review by Rust library/compiler maintainers has occurred.
- The project remains a fork/test branch using nightly-only portable SIMD facilities; green CI does not make its API stable or automatically eligible for stabilization.

## 5. Recommended stabilization roadmap

### Phase 1 — close the current validation loop

1. Obtain a completed green CI run for the current head.
2. Keep the new exhaustive gather/scatter tests and check their results on the complete matrix.
3. Keep validation runs for pushed commits intact. The workflow now uses one concurrency group per workflow and branch with `cancel-in-progress: true`. A newer push supersedes an older queued or running validation so the latest branch head is prioritized; this deliberately does not preserve every intermediate run. Runner capacity can still delay execution, so validation must be checked through completion.
4. Record the final run URL and job counts in this document.

**Exit criteria:** current head has a completed green full matrix, not merely an earlier green commit.

### Phase 2 — security and unsafe-code audit

1. Inventory every `unsafe` block and every unsafe public API in `core_simd`, `std_float`, and architecture-specific modules.
2. For each block, record its invariant: pointer validity, alignment, bounds, initialization, aliasing, provenance, mask validity, lane count, and target-feature preconditions.
3. Add focused tests for each invariant and run Miri where supported.
4. Review pointer casts and layout assumptions against the compiler's documented guarantees.
5. Reproduce historical compiler bugs with minimal examples before changing code around them.

**Exit criteria:** every unsafe site has an explicit, reviewed safety argument and relevant tests; no unexplained unsafe invariant remains.

### Phase 3 — backend, codegen and performance

1. Expand codegen diagnostics beyond the current SSE2 masked-memory sample.
2. Cover AArch64/NEON, WASM SIMD, AVX2/AVX-512 where available, and representative non-power-of-two lane counts.
3. Add controlled benchmarks with repeated runs, stable toolchain/CPU metadata, and scalar baselines.
4. Inspect LLVM IR as well as assembly; record regressions and expected scalar fallbacks.
5. Address #341/#343/#472/#494/#495 only when compiler evidence identifies the responsible layer.

**Exit criteria:** no unexplained major codegen regression in supported targets and repeatable benchmark evidence for every claimed optimization.

### Phase 4 — API and semantics review

1. Reconcile every public API with the intended stable contract: overflow, division by zero, NaNs, rounding, conversions, swizzle OOB behavior, gather/scatter collisions, and mask representation.
2. Resolve or explicitly defer proposals #481, #486, #505, and #539 with maintainer feedback; separately resolve the API-level questions in #364 (lane-count bounds, mask representation, and swizzle shape).
3. Ensure docs and examples do not promise behavior the compiler/backend cannot guarantee.
4. Check semver and compatibility implications before any API change.

**Exit criteria:** all public behavior is specified, testable, and accepted as a coherent standard-library API.

### Phase 5 — upstream preparation

1. Rebase/compare against current `rust-lang/portable-simd` without pushing to upstream.
2. Do not create pull requests as part of this project workflow. Continue with direct commits to this fork's `main` branch only; do not create branches or submit upstream PRs unless the user explicitly changes this instruction.
3. Include tests, Miri results, target matrix, codegen artifacts, benchmark methodology, and issue links.
4. Ask Rust library/compiler maintainers to review compiler-dependent changes and stabilization blockers.
5. Follow the Rust stabilization process through design discussion and maintainer feedback when requested. The fork cannot itself make `std::simd` stable, and this workflow does not create pull requests.

**Exit criteria:** maintainers agree the API and implementation are ready for the appropriate RFC/unstable-feature stabilization process and the required compiler work is merged.

## 6. Timeline estimate

A calendar date for Rust stable would be speculative: stabilization depends on review bandwidth, compiler changes, API consensus, and Rust release process, not only on how quickly this fork's code is edited.

A reasonable planning estimate, assuming regular work and no major compiler blockers:

- **1–3 weeks:** close the current validation loop and complete a first structured unsafe-code audit.
- **3–8 additional weeks:** broaden target-specific codegen/performance evidence and resolve straightforward library-side defects.
- **Several months or longer:** settle compiler-dependent/API issues, obtain upstream review, and go through the Rust stabilization process.

These are planning ranges, not a promise or a prediction of a specific Rust release. If issues #364/#472/#495/#539 require compiler changes or major API redesign, the schedule can extend significantly.

Compared with the first CI, the fork is now much more disciplined: the CI integration problems are understood, the matrix has passed completely at least once, important SIMD edge cases have independent scalar-oracle coverage, and codegen work is based on the fork's own artifacts rather than assumptions.

The most honest description is:

**The project has moved from “initial CI integration and issue reconnaissance” to “broad regression hardening plus targeted codegen work.” It is not yet at “stable-ready for Rust.”**

The next priority is not to add arbitrary SIMD features. It is to finish the current CI run, audit unsafe invariants systematically, and turn the open compiler/API questions into reproducible upstream discussions.

## 9. First-pass unsafe audit status

A source-level inventory has started, covering vector.rs, masks.rs, select.rs, simd/ptr.rs, simd/ptr/const_ptr.rs, simd/ptr/mut_ptr.rs, and std_float/src/lib.rs. A follow-up review has also inspected the unchecked gather/pointer-gather contracts, masked pointer load/store alignment, scatter pointer preconditions, and the architecture-specific dynamic-swizzle feature/width guards. No concrete defect was established in those inspected paths, but this is not a complete audit. The inventory found unsafe operations in the following broad categories:

- SIMD intrinsic calls whose validity and lane-shape contracts must be matched to the compiler intrinsic documentation;
- pointer loads/stores, gather/scatter, and unchecked slice operations requiring bounds, alignment, initialization, aliasing, and provenance arguments;
- mask construction and conversion requiring a proof that every lane contains a valid mask representation;
- pointer/address conversions and provenance exposure/reconstruction;
- SimdElement and MaskElement unsafe trait implementations whose invariants must be checked against every supported scalar type.

A concrete contract gap was found and corrected in the raw-pointer masked load/store wrappers: their intrinsics require base-pointer alignment even when all lanes are disabled. The public safety sections now state this requirement for `load_select_ptr` and `store_select_ptr`, in addition to enabled-lane access validity. This contributes to upstream #381 but does not close the broader safety-documentation review.

This is an inventory, **not a completed safety review**. No unsafe block is being marked sound solely because Miri or ordinary tests pass. The audit must continue through the remaining architecture-specific modules and every unsafe public API, with a written invariant and evidence for each site.
